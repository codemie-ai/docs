# Upgrade LiteLLM from 1.99.2 to 1.105.0

This guide covers database preparation, Helm chart and container image updates, and post-upgrade verification when upgrading LiteLLM from `1.99.2` to `1.105.0`.

## Pre-Upgrade Requirements

Before starting the upgrade:

- Create a complete backup of the LiteLLM database and verify that it can be restored.
- Plan a maintenance window for potential downtime.
- Test the upgrade in a non-production environment.

## 1. Verify Database Table Ownership

Verify that the migration role has the ownership privileges required to alter LiteLLM-managed objects in the target schema. Do not change ownership of unrelated application tables.

Run a diagnostic query under the database role used by the migration Job to check table ownership:

```sql
SELECT
    tablename AS "table",
    tableowner AS "owner"
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY tablename;
```

If ownership changes are required, use an authorized administrative role to transfer ownership of the affected LiteLLM-managed tables only:

```sql
ALTER TABLE public."<table_name>" OWNER TO "<migration_role>";
```

## 2. Database Connection URL Encoding

If the database username contains an `@` character, encode it as `%40` in the username component of `DATABASE_URL`:

- Raw username: `<username>@<domain>`
- Username in `DATABASE_URL`: `<username>%40<domain>`

If `DATABASE_URL` is assembled from a credentials secret, encode only the username value used for URL interpolation.

Keep the raw username for SQL ownership commands and other interfaces that expect a database username. Do not encode an already encoded value again.

## 3. Pre-Upgrade Index Creation

Before upgrading, create the composite index on large `LiteLLM_SpendLogs` tables while LiteLLM `1.99.2` is still running. Both `api_key` and `startTime` columns already exist in this version.

The SQL migration does not create this index. Creating it in advance avoids relying on post-migration index creation and helps reduce upgrade time.

Run these commands in the same database session with autocommit enabled, outside a transaction:

```sql
SET statement_timeout = 0;

CREATE INDEX CONCURRENTLY IF NOT EXISTS
    "LiteLLM_SpendLogs_api_key_startTime_idx"
ON public."LiteLLM_SpendLogs" ("api_key", "startTime");
```

## 4. Update the Helm Chart and Container Image

### Chart Version Changes

Update the following parameters in `litellm/Chart.yaml`:

| Parameter                | Current Value | New Value |
| ------------------------ | ------------- | --------- |
| `version`                | `1.99.0`      | `1.105.0` |
| `appVersion`             | `1.99.2`      | `1.105.0` |
| `dependencies[].version` | `1.99.0`      | `1.105.0` |

Keep the dependency repository unchanged:

```yaml
repository: oci://ghcr.io/berriai
```

### Container Image Version

Update `litellm/values-<cloud_name>.yaml` for your cloud provider: `aws`, `azure`, or `gcp`.

| Parameter                | Current Value | New Value |
| ------------------------ | ------------- | --------- |
| `litellm-helm.image.tag` | `1.99.2`      | `1.105.0` |

The updated configuration should contain:

```yaml
litellm-helm:
  image:
    tag: "1.105.0"
```

### Apply the Upgrade

Run the following command from the `codemie-helm-charts` directory, replacing `<cloud_name>` with your cloud provider:

```bash
helm upgrade --install litellm ./litellm \
  --namespace litellm \
  --values ./litellm/values-<cloud_name>.yaml \
  --wait \
  --timeout 900s \
  --dependency-update
```

Use the existing release name and namespace if they differ from the example.

Wait for the migration Job to complete successfully and the updated LiteLLM pods to become ready before proceeding.

## 5. Post-Upgrade Index Creation

After upgrading to LiteLLM `1.105.0` and completing schema migrations, ensure that the `litellm_call_id` index exists by running the commands below.

Run these commands in the same database session with autocommit enabled, outside a transaction:

```sql
SET statement_timeout = 0;

CREATE INDEX CONCURRENTLY IF NOT EXISTS
    "LiteLLM_SpendLogs_litellm_call_id_idx"
ON public."LiteLLM_SpendLogs" ("litellm_call_id");
```

:::info
Run this step only after schema migrations have completed. The `litellm_call_id` column does not exist in `1.99.2` and is added during the upgrade.
:::

## 6. Post-Upgrade Verification

Verify that both indexes are created, valid, and ready for queries:

```sql
SELECT
    i.relname AS index_name,
    idx.indisvalid AS is_valid,
    idx.indisready AS is_ready,
    pg_size_pretty(pg_relation_size(i.oid)) AS index_size,
    pg_get_indexdef(i.oid) AS definition
FROM pg_index idx
JOIN pg_class i ON i.oid = idx.indexrelid
WHERE idx.indrelid = 'public."LiteLLM_SpendLogs"'::regclass
  AND i.relname IN (
      'LiteLLM_SpendLogs_api_key_startTime_idx',
      'LiteLLM_SpendLogs_litellm_call_id_idx'
  );
```

Expected output:

- Two rows, with both `is_valid` and `is_ready` set to `true`.
- `LiteLLM_SpendLogs_api_key_startTime_idx` indexes `api_key` and `startTime`, in that order.
- `LiteLLM_SpendLogs_litellm_call_id_idx` indexes `litellm_call_id`.

The `index_size` column shows the disk space used by each index.

If either index is missing or either flag is `false`, investigate the index creation logs before considering the upgrade complete.
